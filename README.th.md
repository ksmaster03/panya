# panya (ปัญญา)

[English](README.md) · **ภาษาไทย**

![หัวหุ่นยนต์ที่เชื่อมกับสมองก้อนที่สองซึ่งประกอบจากการ์ดบันทึกและฐานข้อมูลขนาดเล็ก](docs/panya-hero.jpg)

**panya** คือสมองที่สองของแอป AI เป็นบริการความจำที่เก็บข้อเท็จจริง ค้นคืนได้ และตอบว่า "ไม่รู้" เมื่อไม่มีความจำที่เกี่ยวข้อง ทั้งหมดนี้ทำ**โดยไม่เรียก LLM** จึงไม่เขียนข้อความของคุณใหม่ และไม่แต่งรายละเอียดขึ้นเอง

ออกแบบมาสำหรับข้อความไทยและอังกฤษ ทำงานบน Bun, TypeScript และ [seekdb](https://github.com/oceanbase/seekdb)

เปิดซอร์สให้อ่านและใช้ฟรีสำหรับงานที่ไม่ใช่เชิงพาณิชย์ ส่วน[การใช้เพื่อธุรกิจต้องซื้อสิทธิ์ใช้งาน](COMMERCIAL.md)

## ทำไมต้องมี

ระบบความจำที่ใช้ LLM จะอ่านข้อความของคุณแล้วเขียนฉบับของมันเอง ตอนทดลองกับเครื่องมือแบบนั้นตัวหนึ่ง ข้อความ "ปิดซ่อมถึงวันพุธ" กลับออกมาเป็น "ปิดซ่อมถึงวันพุธที่ 11 ตุลาคม" ซึ่งไม่มีใครเขียนวันที่นั้นไว้ การบันทึกแต่ละครั้งใช้ 18 ถึง 25 วินาที และคำถามนอกเรื่องก็ยังได้ความจำกลับมาสามข้อ

panya เลือกทางตรงข้าม

- **เก็บตามต้นฉบับ** `text` ที่ได้คืนตรงกับที่ส่งมาทุกตัวอักษร
- **ใช้กฎแทนโมเดล** ในการอัปเดต การหมดอายุ ของซ้ำ และรหัส
- **รู้จักไม่ตอบ** การค้นคืนค่าว่างได้ พร้อมเหตุผล

## ทำอะไรได้

- ค้นแบบผสม: ค้นด้วยคำ (ตัดคำไทย) ร่วมกับ embedding หลายภาษาที่รันในเครื่อง
- ข้อเท็จจริงมีคีย์: ค่าใหม่ของ `subject` + `attribute` เดิมจะแทนค่าเก่า และเก็บประวัติไว้
- หมดอายุ: ความจำที่เลย `validUntil` จะไม่ถูกคืน
- รวมข้อความซ้ำที่ไม่มีคีย์
- กฎรหัส: ถ้าคำค้นระบุรหัส (`D-04`, `70-1234`, `BK-2026-0912`) ความจำที่ไม่มีรหัสนั้นถูกตัดออก
- ทะเบียนชื่อเฉพาะ: รู้จักลูกค้าและผู้ขนส่งตามชื่อ และไม่ตอบเมื่อถูกถามถึงชื่อที่ไม่เคยเห็น
- แยก tenant ที่ฝั่งเซิร์ฟเวอร์ ผูก API key กับ container เดียวได้

## เริ่มใช้

ต้องมี [Bun](https://bun.sh) และ Docker

```bash
bun install
docker volume create panya-seekdb-data
bun run db:up                 # seekdb ที่ 127.0.0.1:2881 บูตราว 30 วินาที
cp .env.example .env          # ตั้ง PANYA_API_KEYS
bun run dev                   # http://127.0.0.1:6800
```

```bash
bun run test        # ต้องมี seekdb รันอยู่
bun run typecheck
bun run eval        # วัดคุณภาพการค้นคืนบน eval/dataset.json
bun run bench       # วัดความเร็ว
```

## API

ทุกเส้นทางใต้ `/v1` ต้องมี `Authorization: Bearer <key>`

| เส้นทาง | ใช้ทำอะไร |
|---|---|
| `POST /v1/memories` | บันทึก `{ container, text, subject?, attribute?, kind?, validUntil?, source? }` |
| `POST /v1/memories/batch` | บันทึกครั้งละไม่เกิน 200 รายการ `{ container, memories: [...] }` ถ้ามีรายการผิดรูปแบบจะไม่บันทึกเลย |
| `POST /v1/search` | `{ container, q, limit? }` ได้ `{ hits, abstained, reason? }` |
| `GET /v1/profile?container=` | ความชอบ ข้อเท็จจริงมีคีย์ และรายการล่าสุด |
| `PUT /v1/entities` | ลงทะเบียนชื่อ `{ container, type, cues, names }` |
| `GET /v1/entities?container=` | ดูชื่อที่ลงทะเบียนไว้ |
| `DELETE /v1/memories/:id?container=` | ลบความจำหนึ่งรายการ |

API key ตั้งใน `PANYA_API_KEYS` คั่นด้วยจุลภาค แบบ `key` ใช้ได้ทุก container แบบ `key@container` ใช้ได้กับ container นั้นเท่านั้น

## ตัดสินใจอย่างไร

1. ตัดคำของคำค้น ภาษาไทยใช้ `Intl.Segmenter` ส่วนรหัสเก็บไว้ทั้งก้อน
2. ถ้าคำค้นมีชื่อที่ลงทะเบียนไว้ จะเหลือเฉพาะความจำที่พูดถึงชื่อนั้น ถ้าคำนำหน้าอย่าง "ลูกค้า" ตามด้วยคำที่ไม่เคยปรากฏในความจำของ container นี้เลย จะไม่ตอบ พร้อม `reason: "unknown_entity"`
3. ดึงผู้สมัครจากความคล้ายของเวกเตอร์และจากการค้นด้วยคำ
4. ตัดผู้สมัครที่ไม่มีรหัสตามที่คำค้นถาม
5. ให้คะแนนจากความคล้ายที่ปรับสเกลแล้ว รวมกับสัดส่วนคำของคำค้นที่พบในความจำ รายการที่ต่ำกว่า `minScore` ถูกทิ้ง ถ้าไม่เหลือเลยจะได้ `abstained: true`

เกณฑ์อยู่ใน `src/config.ts` และได้มาจาก `bun run eval` ซึ่งปรับบนคำถามครึ่งหนึ่งแล้วรายงานผลบนอีกครึ่ง

## ผลวัด

ความจำไทยสมมติ 100 ข้อ และคำถาม 120 ข้อ (ใช้คำตรงกัน 36 ถามด้วยคำอื่น 42 นอกเรื่อง 16 อยู่ในโดเมนแต่ไม่มีคำตอบ 26) ตัวเลขด้านล่างมาจากคำถาม 60 ข้อที่ไม่ได้ใช้ปรับเกณฑ์ วัดเมื่อ 7 ตุลาคม 2026 บนโน้ตบุ๊ก Windows

| ชุดที่ไม่ได้ใช้ปรับเกณฑ์ | panya | supermemory ค่าตั้งต้น | supermemory ตั้งเกณฑ์คะแนน |
|---|---|---|---|
| ถูกที่อันดับ 1 | 82% | 85% | 44% |
| ถูกใน 3 อันดับแรก | 90% | 92% | 44% |
| ไม่ตอบทั้งที่มีคำตอบ | 10% | 3% | 56% |
| ไม่ตอบเมื่อไม่มีคำตอบ | 76% | 0% | 100% |
| เวลาค้นเฉลี่ย | 20 ms | 78 ms | 78 ms |

อ่านผลนี้ตามจริง panya **ไม่ได้**จัดอันดับเก่งกว่าตัวเทียบ การจัดอันดับพอ ๆ กัน สิ่งที่เพิ่มเข้ามาคือความสามารถในการไม่ตอบ ซึ่งเกณฑ์คะแนนค่าเดียวทำไม่ได้โดยไม่ทิ้งคำตอบจริงไปเกินครึ่ง

ตัวเทียบคือ supermemory แบบ self-host รุ่น 0.0.8 โหมดค้นเอกสาร ใช้ `multilingual-e5-base` และไม่ได้ตั้ง LLM โหมดสกัดความจำด้วย LLM ของมันยังไม่ได้วัด เพราะบน Gemini key แบบฟรีประมวลผลได้ราวนาทีละหนึ่งความจำ จึงหยุดไว้ก่อน

รันซ้ำได้ด้วย `bun run eval` และ `bun eval/baseline-supermemory.ts ingest|measure`

ความเร็ว จาก `bun run bench` เมื่อ 8 ตุลาคม 2026 (เครื่องเดิม seekdb รันใน Docker)

| การทำงาน | เวลา |
|---|---|
| ค้น คำค้นใหม่ | เฉลี่ย 18 ms, p95 30 ms |
| ค้น คำค้นซ้ำ (จำ embedding ไว้แล้ว) | เฉลี่ย 9 ms, p95 14 ms |
| ยิงค้น 120 คำค้นพร้อมกัน | 236 คำค้นต่อวินาที |
| บันทึกทีละรายการ | 25 ms ต่อรายการ |
| บันทึกผ่านเส้นทาง batch | 12 ms ต่อรายการ |

หน่วยความจำ: โปรเซส panya ใช้ราว 1 GB และ seekdb ระบุขั้นต่ำ 2 GB

## ข้อจำกัดที่รู้แล้ว

- คำถามที่ใช้คำห่างจากต้นฉบับมากยังพลาด (คำถามแบบถามด้วยคำอื่นถูกที่อันดับ 1 เพียง 67%)
- คำถามในโดเมนที่ไม่มีคำตอบยังถูกตอบราวหนึ่งในสี่ เช่น ถามจำนวนรถของผู้ขนส่งรายหนึ่ง จะได้ข้อเท็จจริงอื่นของรายนั้นกลับมา
- ตัวเลขโดดและตัวอักษรเดี่ยว ("ประตู 5", "โซน Z") ยังไม่ถูกมองเป็นรหัส
- ย่อข้อความเองไม่ได้ ให้ส่งมาทีละข้อเท็จจริงสั้น ๆ ไม่เกิน 2000 ตัวอักษร
- seekdb โหมด embedded ค้างบน Windows ทั้งใต้ Bun และ Node (ทดสอบ 7 ตุลาคม 2026) ให้ใช้แบบเซิร์ฟเวอร์ใน Docker
- image `oceanbase/seekdb` ไม่ใช้ค่า `ROOT_PASSWORD` ในการทดสอบของเรา รหัส root ว่างเปล่า ต้องตั้งด้วย SQL ก่อนเปิดพอร์ตให้เครื่องอื่น
- ชุดวัดผลยังเล็กและมาจากโดเมนเดียว ควรรันกับข้อมูลของคุณเองก่อนเชื่อเกณฑ์
