# panya (ปั้นหยา)

[English](README.md) · **ภาษาไทย**

![หัวหุ่นยนต์ที่เชื่อมกับสมองก้อนที่สองซึ่งประกอบจากการ์ดบันทึกและฐานข้อมูลขนาดเล็ก](docs/panya-hero.jpg)

**panya** คือสมองที่สองของแอป AI เป็นบริการความจำที่เก็บข้อเท็จจริง ค้นคืนได้ และตอบว่า "ไม่รู้" เมื่อไม่มีความจำที่เกี่ยวข้อง ทั้งหมดนี้ทำ**โดยไม่เรียก LLM** จึงไม่เขียนข้อความของคุณใหม่ และไม่แต่งรายละเอียดขึ้นเอง

ออกแบบมาสำหรับข้อความไทยและอังกฤษ ทำงานบน Bun, TypeScript และ [seekdb](https://github.com/oceanbase/seekdb)

เปิดซอร์สให้อ่านและใช้ฟรีสำหรับงานที่ไม่ใช่เชิงพาณิชย์ ส่วน[การใช้เพื่อธุรกิจต้องซื้อสิทธิ์ใช้งาน](COMMERCIAL.md)

## ทำไมต้องมี

ระบบความจำที่ใช้ LLM จะอ่านข้อความของคุณแล้วเขียนฉบับของมันเอง ตอนทดลองกับเครื่องมือแบบนั้นตัวหนึ่ง ข้อความ "ปิดซ่อมถึงวันพุธ" กลับออกมาเป็น "ปิดซ่อมถึงวันพุธที่ 11 ตุลาคม" ซึ่งไม่มีใครเขียนวันที่นั้นไว้ การบันทึกแต่ละครั้งใช้ 18 ถึง 25 วินาที และคำถามนอกเรื่องก็ยังได้ความจำกลับมาสามข้อ

panya เลือกทางตรงข้าม

- **เก็บตามต้นฉบับ** `text` ที่ได้คืนตรงกับที่ส่งมาทุกตัวอักษร
- **ใช้กฎแทนโมเดล** ในการอัปเดต การหมดอายุ ของซ้ำ และรหัส
- **รู้จักไม่ตอบ** การค้นคืนค่าว่างได้ พร้อมเหตุผล

## ทำอะไรได้

- ค้นแบบผสม: ค้นด้วยคำ (ตัดคำไทย) ร่วมกับ embedding หลายภาษาที่รันในเครื่อง
- ข้อเท็จจริงมีคีย์: ค่าใหม่ของ `subject` + `attribute` เดิมจะแทนค่าเก่า และเก็บประวัติไว้
- หมดอายุ: ความจำที่เลย `validUntil` จะไม่ถูกคืน
- รวมข้อความซ้ำที่ไม่มีคีย์
- กฎรหัส: ถ้าคำค้นระบุรหัส (`D-04`, `70-1234`, `BK-2026-0912`) ความจำที่ไม่มีรหัสนั้นถูกตัดออก
- ทะเบียนชื่อเฉพาะ: รู้จักลูกค้าและผู้ขนส่งตามชื่อ และไม่ตอบเมื่อถูกถามถึงชื่อที่ไม่เคยเห็น
- แยก tenant ที่ฝั่งเซิร์ฟเวอร์ ผูก API key กับสมองเดียวได้
- ข้อมูลเป็นของคุณ ส่งออกทั้งสมองเป็น JSON แล้วนำเข้าที่ไหนก็ได้

## เริ่มใช้

ต้องมี [Bun](https://bun.sh) และ Docker

```bash
bun install
docker volume create panya-seekdb-data
bun run db:up                 # seekdb ที่ 127.0.0.1:2881 บูตราว 30 วินาที
cp .env.example .env          # ตั้ง PANYA_API_KEYS
bun run dev                   # http://127.0.0.1:6800
```

```bash
bun run test        # ต้องมี seekdb รันอยู่
bun run typecheck
bun run eval        # วัดคุณภาพการค้นคืนบน eval/dataset.json
bun eval/run.ts --rerank --haystack <brain>[:<count>]   # วัดแบบเดียวกัน พร้อม reranker และความจำจริงเป็นตัวลวง
bun run bench       # วัดความเร็ว
```

`--haystack <brain>[:<count>]` นำความจำจริงจากสมองใบหนึ่งของคุณมาปนในชุดวัดผลเป็นตัวลวง โดยอ่านจากฐานข้อมูลตอนรัน ลบออกเมื่อวัดเสร็จ และไม่เขียนลงไฟล์ใดเลย

## แอป Windows (ไม่ต้องมี Docker)

`windows/` สร้างตัวติดตั้งแอป Windows แบบติดตั้งให้ผู้ใช้คนเดียว ไม่ต้องมี Docker และไม่ต้องใช้สิทธิ์ผู้ดูแลเครื่อง

```bash
bun windows/build.ts        # ใช้ได้บน Windows x64 เท่านั้น → dist/windows/Panya-Setup.exe
```

ตอนสร้างจะคัดลอก `src/` ติดตั้งเฉพาะ dependency ที่ใช้จริง เก็บไว้เฉพาะไฟล์ native ของ Windows x64 รวมโมเดล `multilingual-e5-small` ไว้ในชุดติดตั้ง (เปิดครั้งแรกจึงไม่ต้องดาวน์โหลดอะไร) แล้วคอมไพล์โปรแกรมสองตัวด้วย `bun build --compile` `Panya.exe` เป็นทั้งตัวเปิดแอปและ runtime โดยเรียกตัวเองให้ทำงานเป็น Bun (`BUN_BE_BUN=1`) เพื่อรันเซิร์ฟเวอร์ จึงไม่ต้องพก `bun.exe` อีกตัว

ตัวติดตั้งทำอะไรบ้าง

- แตกไฟล์ไปที่ `%LOCALAPPDATA%\Programs\Panya` ด้วย `tar.exe` ที่มากับ Windows 10 และ 11 สร้างทางลัดในเมนู Start และบนเดสก์ท็อป (Panya, Stop Panya, Panya settings, Uninstall Panya) และลงทะเบียนใน Settings > Apps แล้วถามว่าจะให้เปิด Panya ทุกครั้งที่ล็อกอิน Windows หรือไม่ ตัวเลือก: `--yes` `--no-autostart` `--no-launch`
- เก็บความจำด้วย SQLite (`PANYA_STORE=sqlite`) ไว้ที่ `%LOCALAPPDATA%\Panya\data` แยกจากตัวโปรแกรม ติดตั้งรุ่นใหม่ทับรุ่นเก่าแล้วความจำยังอยู่ ค่าตั้งอยู่ใน `%LOCALAPPDATA%\Panya\panya.env` (พอร์ต และ `PANYA_HOST=0.0.0.0` ถ้าจะให้เครื่องอื่นในวงแลนเข้าได้) บันทึกการทำงานอยู่ที่ `logs\panya.log`
- เปิดครั้งแรก หน้าเข้าสู่ระบบจะเป็นหน้าตั้งค่าสำหรับสร้างบัญชีผู้ดูแล (`PANYA_SETUP=local`) รับเฉพาะคำขอจากเครื่องนี้เอง โดยดูจากที่อยู่ของการเชื่อมต่อจริง และปิดตัวเองทันทีที่มีผู้ใช้คนแรก
- ถอนการติดตั้งได้จาก Settings > Apps หรือเมนู Start ความจำจะเก็บไว้ ยกเว้นสั่ง `Panya.exe --uninstall --purge`

ผลวัดบนเครื่องนี้ (Windows 11 ไม่มีการ์ดจอแยก): ตัวติดตั้ง 271 MB ติดตั้งเสร็จใน 12 วินาที เซิร์ฟเวอร์พร้อมใช้ราว 3.5 วินาทีหลังเปิด ใช้หน่วยความจำราว 750 MB ชุดเทสต์ทั้งหมดผ่านกับที่เก็บแบบ SQLite ด้วย (`PANYA_STORE=sqlite PANYA_DATA_DIR=<โฟลเดอร์ชั่วคราว> bun test`) ทดสอบกับความจำสังเคราะห์ 30,000 รายการในสมองใบเดียว ค้นด้วยเวกเตอร์ใช้ราว 40 มิลลิวินาทีเมื่อเวกเตอร์อยู่ในหน่วยความจำแล้ว (ครั้งแรกหลังเปิดราว 0.4 วินาที) ค้นด้วยคำ 0.2 ถึง 0.3 วินาที

ที่เก็บแบบ SQLite (`src/sqlite.ts`) ทำเฉพาะส่วนของ API collection ของ seekdb ที่ panya ใช้จริง เทียบเวกเตอร์ทีละรายการในหน่วยความจำแทนดัชนี HNSW และจับคำผ่านตารางคำที่ตัดไว้แล้ว ให้คะแนนแบบ BM25 พอสำหรับหลักหมื่นรายการต่อสมอง ถ้าเป็นเซิร์ฟเวอร์กลางที่มีสมองใหญ่หลายใบ ให้ใช้ seekdb ต่อ จะย้ายความจำจากเครื่องที่ใช้ Docker ให้ใช้ `GET /v1/export` ที่เครื่องเดิม แล้ว `POST /v1/import` ในแอป

ยังไม่ได้ทำ: ตัวติดตั้งและ `Panya.exe` ยังไม่ได้เซ็นรับรองโค้ด Windows SmartScreen จึงขึ้นหน้า "Windows protected your PC" (กด More info แล้ว Run anyway) การถอดเสียงจากไฟล์เสียงและวิดีโอยังต้องมี Python กับ `faster-whisper` และการอ่านข้อความในภาพต้องมี Tesseract บนเครื่องนั้น seekdb เองมีโหมดฝังในโปรแกรม (embedded) ที่ระบุว่ารองรับ Windows แต่บนเครื่องนี้ค้างตอนเริ่มทั้งใน Bun และ Node แอปจึงใช้ SQLite แทน

## เริ่มอัตโนมัติบน Windows

`scripts/start-panya.ps1` เปิด Docker Desktop ถ้ายังไม่ได้รัน สั่งคอนเทนเนอร์ seekdb ขึ้น รอจนพร้อม แล้วคอยให้ `bun src/index.ts` รันอยู่ตลอด ถ้าล่มจะเริ่มใหม่ใน 15 วินาที ผลลัพธ์เขียนลง `logs/panya.log`

ถ้าจะให้รันทุกครั้งที่ล็อกออนโดยไม่ต้องใช้สิทธิ์แอดมิน ให้วางไฟล์ `.vbs` เล็ก ๆ ไว้ในโฟลเดอร์ Startup (กด Win+R แล้วพิมพ์ `shell:startup`):

```vbs
Set WshShell = CreateObject("WScript.Shell")
WshShell.Run "powershell.exe -NoProfile -ExecutionPolicy Bypass -WindowStyle Hidden -File ""<path-to-repo>\scripts\start-panya.ps1""", 0, False
```

สคริปต์เริ่มตอนผู้ใช้ล็อกออน ไม่ใช่ตอนเครื่องบูต และ Docker Desktop เองก็ต้องมีผู้ใช้ล็อกออนอยู่ ถ้าจะหยุด panya ให้ปิดตัว `powershell` ที่เป็นตัวเรียกก่อน แล้วค่อยปิด `bun` ไม่อย่างนั้นตัวเรียกจะเปิดขึ้นมาใหม่

## รันด้วย Docker

`Dockerfile` สร้าง image ที่ฝังโมเดล embedding ไว้แล้ว ตอนเปิดจึงไม่ต้องต่ออินเทอร์เน็ต ส่วน `deploy/docker-compose.prod.yml` รัน panya กับ seekdb ข้างแอปที่มีอยู่บนเครื่องเดียวกัน ไม่เปิดพอร์ตออกนอกเครื่อง แอปเรียก panya ที่ `http://panya:6800` ผ่านเครือข่าย Docker ของแอปเอง และทั้งสองคอนเทนเนอร์มีเพดาน RAM

```bash
cd deploy
printf 'PANYA_API_KEYS=%s
' "$(openssl rand -hex 32)" > .env && chmod 600 .env
APP_NETWORK=<เครือข่าย docker ของแอป> docker compose -f docker-compose.prod.yml up -d --build
```

วัดเมื่อ 8 ตุลาคม 2026 ด้วยความจำ 2,000 ข้อ และยิงค้นพร้อมกัน 360 ครั้งภายใต้เพดานนั้น: panya ใช้ราว 575 MB และ seekdb ราว 160 MB

## API

ทุกเส้นทางใต้ `/v1` ต้องมี `Authorization: Bearer <key>`

| เส้นทาง | ใช้ทำอะไร |
|---|---|
| `POST /v1/memories` | บันทึก `{ brain, text, subject?, attribute?, kind?, validUntil?, source?, ref?, panya? }` |
| `POST /v1/documents` | ตัดเอกสารยาวเป็นท่อนแล้วเก็บ: `{ brain, text, source, panya?, max?, overlap?, headings? }` ดู [เอกสารยาวและการตัดท่อน](#เอกสารยาวและการตัดท่อน) |
| `POST /v1/files` | ส่งไฟล์ (multipart: `file`, `brain`, `source?`, `panya?`, `kind?`) ได้ทั้งเอกสาร เสียง วิดีโอ และภาพ ได้งาน (job) กลับมา ใส่ `?wait=1` เพื่อรอจนเสร็จ ดู [ไฟล์](#ไฟล์-เอกสาร-เสียง-วิดีโอ-ภาพ) |
| `GET /v1/files/jobs/:id` | สถานะงาน: `queued` `running` (มี `progress`) `done` หรือ `error` |
| `GET /v1/files/types` | ชนิดไฟล์ที่เซิร์ฟเวอร์นี้อ่านได้ และเปิดเสียง/ภาพไว้หรือไม่ |
| `PATCH /v1/memories/:id` | ตั้งหรือล้างป้ายหมวดปัญญา: `{ brain, panya }` |
| `POST /v1/memories/batch` | บันทึกครั้งละไม่เกิน 200 รายการ `{ brain, memories: [...] }` ถ้ามีรายการผิดรูปแบบจะไม่บันทึกเลย |
| `POST /v1/search` | `{ brain, q, limit?, minScore?, rerank?, panya? }` ได้ `{ hits, abstained, reason? }` ส่ง `rerank: false` เพื่อข้าม reranker (ตัวเลือกเสริม) เฉพาะคำขอนั้น |
| `GET /v1/graph?brain=` | จุดความจำพร้อมตำแหน่ง 2 มิติและเส้นเชื่อมเพื่อนบ้าน สำหรับหน้าสมอง |
| `GET /v1/points?brain=` | ทุกความจำที่ยังใช้ได้เป็นจุด 2 มิติ (PCA ของ embedding ทั้งชุด) พร้อมหมวดและวันที่ และเส้นเชื่อมเพื่อนบ้านจากตัวอย่างที่กระจายทั่วชุด ไม่มีข้อความความจำ คำนวณตอนเปิดเซิร์ฟเวอร์และเก็บผลไว้ 10 นาที |
| `GET /v1/memories/:id?brain=` | ความจำหนึ่งรายการ ใช้แสดงข้อความเมื่อชี้จุดบนแดชบอร์ด |
| `GET /v1/profile?brain=` | ความชอบ ข้อเท็จจริงมีคีย์ และรายการล่าสุด |
| `PUT /v1/entities` | ลงทะเบียนชื่อ `{ brain, type, cues, names }` |
| `GET /v1/entities?brain=` | ดูชื่อที่ลงทะเบียนไว้ |
| `GET /v1/export?brain=` | ทุกอย่างในสมองเป็น JSON (`&history=1` รวมรุ่นที่ถูกแทนแล้ว) |
| `POST /v1/import` | นำไฟล์ส่งออกกลับเข้า `{ brain, memories, entities?, replace? }` ครั้งละไม่เกิน 5000 รายการ |
| `GET /v1/stats?brain=` | จำนวนความจำที่ยังใช้ได้ |
| `DELETE /v1/memories/:id?brain=` | ลบความจำหนึ่งรายการ |
| `DELETE /v1/sources?brain=&source=` | ลบทุกรายการที่มาจากแหล่งเดียวกัน |
| `DELETE /v1/brain?brain=&confirm=` | ล้างทั้งสมอง ต้องส่งชื่อสมองซ้ำใน `confirm` |

**สมอง (brain)** คือชุดความจำที่แยกขาดจากกันหนึ่งชุด เช่นของลูกค้าหนึ่งราย โปรเจกต์หนึ่ง หรือ agent หนึ่งตัว API key ตั้งใน `PANYA_API_KEYS` คั่นด้วยจุลภาค แบบ `key` ใช้ได้ทุกสมอง แบบ `key@brain` ใช้ได้กับสมองนั้นเท่านั้น ชื่อฟิลด์ `container` ของรุ่นก่อนยังใช้ได้

## หน้าสมอง

เปิด `http://127.0.0.1:6800/brain` แล้วเข้าสู่ระบบด้วยชื่อสมองกับ API key ของสมองนั้น มีปุ่มส่งออกทั้งสมองเป็นไฟล์ JSON และปุ่ม **เพิ่มไฟล์** (หรือลากไฟล์มาวางบนภาพสมอง) ที่ส่งเอกสาร เสียง วิดีโอ และภาพไปที่ `/v1/files` ความจำแต่ละข้อคือจุดหนึ่งจุดในโครงสมอง ความจำที่ความหมายใกล้กันจะอยู่ใกล้กันและมีเส้นเชื่อม พิมพ์คำถามแล้วจุดที่เกี่ยวข้องจะสว่างขึ้น หรือหน้าจะบอกว่าสมองเลือกไม่ตอบ ตัวหน้าไม่มีข้อมูลฝังอยู่ ทุกอย่างมาจาก `/v1/graph` และ `/v1/search` ด้วย key ของคุณ

## นำเข้าความจำของ Claude Code

```bash
bun run import:claude-memory --dry          # นับก่อนว่าจะนำเข้าเท่าไร
bun run import:claude-memory                # ทุกโฟลเดอร์ ~/.claude/projects/*/memory
bun run import:claude-memory <โฟลเดอร์> --brain my-notes
```

แต่ละไฟล์กลายเป็นความจำสั้นหลายข้อ (คำอธิบายของไฟล์ และเนื้อหาที่ตัดตามย่อหน้า) โทเคนและ key ถูกแทนด้วย `[redacted]` ก่อนเก็บ รันซ้ำจะแทนที่ของเดิมจากไฟล์เดียวกัน ข้อมูลอยู่ใน seekdb ในเครื่องของคุณเท่านั้น

## แดชบอร์ด

เปิด `http://127.0.0.1:6800/dashboard` แล้วเข้าสู่ระบบด้วย API key หน้านี้แสดงสมองทุกใบที่ key เข้าถึงได้: สมองกลางสามมิติมีลูกทรงกลมแทนสมองแต่ละใบ ความจำที่วิ่งเข้า (เขียน) และออก (ค้น) ตามที่เกิดขึ้นจริง ฟีดสด แถบคลื่นสัญญาณ กราฟการเขียนและการค้น และตารางสถิติที่เรียงได้ สลับไทย/อังกฤษได้ที่หัวหน้า ข้อมูลมาจาก `GET /v1/overview` (สถิติ เก็บผลไว้ห้าวินาที) และ `GET /v1/events` (การเขียน ค้น และลบ 300 รายการล่าสุดที่ผ่านเซิร์ฟเวอร์นี้ เก็บในหน่วยความจำ รีสตาร์ตแล้วหาย)

แถวปุ่มเหนือตัวเลขใช้สลับระหว่างดูทุกสมองกับดูทีละสมอง ตัวเลข กราฟ ฟีดสด แถบสัญญาณ และลูกทรงกลมที่เด่นขึ้นจะเปลี่ยนตามสมองที่เลือก และตัวเลือกอยู่ใน URL (`/dashboard?brain=<ชื่อ>`) ส่งลิงก์ให้คนอื่นเปิดหน้าเดียวกันได้ กดลูกทรงกลมหรือแถวในตารางก็เลือกสมองนั้นได้เช่นกัน

สมองสามมิติตรงกลางแสดงทุกความจำที่ยังใช้ได้ของสมองที่เลือกเป็นจุดสี (สีตามหมวด แบบเดียวกับหน้า `/brain`) พร้อมเส้นเชื่อมเพื่อนบ้านและสัญญาณที่วิ่งไปตามเส้น เมื่อมีหลายหมื่นจุดจะวาดเป็นสี่เหลี่ยมเล็กแทนแสงเรืองเพื่อให้ภาพยังลื่น (ราว 21 fps ที่ 23,648 จุดบน CPU โน้ตบุ๊ก) ตัวอย่างขึ้นก่อนแล้วชุดครบจะแทนที่เมื่อพร้อม ผู้ชมที่ไม่มี key เห็นแค่ตำแหน่ง หมวด และวันที่ ส่วนผู้ที่ใช้ key ชี้ที่จุดแล้วจะเห็นข้อความ

## หน้าคลังสินค้า

เปิด `http://127.0.0.1:6800/warehouse` จะเห็นข้อมูลชุดเดียวกันในรูปคลังสินค้าสามมิติ (Three.js r170 เก็บไว้ใน `src/assets` ไม่ต้องใช้อินเทอร์เน็ต): สมองแต่ละใบคือหนึ่งโซนที่มีประตูรับของและรถยกของตัวเอง หมวดแต่ละหมวดคือหนึ่งชั้นวาง (9 หมวดใหญ่สุดต่อสมอง ที่เหลือรวมเป็น "อื่น ๆ") และกล่องหนึ่งใบแทนความจำจำนวนคงที่ตามที่แสดงบนจอ (100 รายการต่อกล่องเมื่อมี 41,871 รายการ) กล่องที่เข้ามาใน 24 ชั่วโมงเป็นสีอ่อน เมื่อมีการบันทึกจริง รถยกของโซนนั้นจะขนกล่องจากประตูไปวางที่ชั้นของหมวดนั้น เมื่อมีการค้น ชั้นของสมองนั้นจะเรืองแสง กดที่ชั้นวางเพื่อดูจำนวน สัดส่วนในโซน และเวลาที่รับเข้าล่าสุด สิทธิ์การเข้าดูเหมือนแดชบอร์ด ใช้ข้อมูลจาก `/v1/overview`, `/v1/points` และ `/v1/events`

ถ้าอยากให้ดูแดชบอร์ดได้โดยไม่ต้องใช้ key ตั้ง `PANYA_PUBLIC_DASHBOARD=lan` (ไม่ต้องใช้ key เมื่อเปิดจากเครื่องนี้หรือที่อยู่ในเครือข่ายภายใน) หรือ `all` จะเปิดเฉพาะ `GET /v1/overview` และ `GET /v1/events` แบบอ่านอย่างเดียว แต่ฟีดสดจะแสดงข้อความความจำและคำถามที่ค้นให้ทุกคนที่เข้าหน้านี้ได้เห็น `lan` ดูจากที่อยู่ของการเชื่อมต่อจริง ถ้าวางหลัง reverse proxy ทุกคำขอจะดูเหมือนมาจากภายใน จึงไม่ควรใช้แบบนั้น คำขอที่ส่ง key ผิดมายังถูกปฏิเสธเหมือนเดิม

ด้านล่างของแดชบอร์ดมีแถบเสียง: ปุ่มเล่น/หยุด รูปคลื่นของทั้งเพลงที่คลิกเพื่อข้ามไปตำแหน่งที่ต้องการได้ แท่งความถี่แบบสด และปุ่มปรับระดับเสียง แถบนี้เล่นไฟล์ `src/assets/mr-scratch.mp3` ซึ่งให้บริการที่ `GET /assets/<file>` (เฉพาะไฟล์ mp3, ogg และ wav ใน `src/assets` และรองรับ Range) ไฟล์เสียงไม่ได้รวมอยู่ใน repository ให้วางไฟล์ของคุณเองไว้ที่ path นั้น

## skill สำหรับ Claude Code

โฟลเดอร์ `skills/` มี skill ตัวอย่างสองตัว ให้ Claude Code บนเครื่องใดก็ได้รับส่ง skill และ memory ผ่าน panya ตัวเดียวกันทาง HTTP API คัดลอกโฟลเดอร์ไปไว้ที่ `~/.claude/skills/` แล้วรัน `setup` หนึ่งครั้ง:

```bash
node ~/.claude/skills/panya-memory/scripts/panya-memory.mjs setup --url http://<host>:6800 --key <api key>
```

| skill | ส่ง | รับ |
|---|---|---|
| `panya-skills` | `push` ทุก `SKILL.md` และ command เข้า brain `claude-skills` | `list`, `search`, `show <ชื่อ>` หรือ `pull <ชื่อ>` เพื่อติดตั้งลงเครื่อง |
| `panya-memory` | `push` ไฟล์ความจำของ Claude Code หรือ `remember "<ข้อเท็จจริง>"` | `search "<คำถาม>"`, `list`, `show` หรือ `pull <โปรเจกต์> --to <โฟลเดอร์>` |

ทั้งสองตัวใช้แค่ Node 18 ขึ้นไป ส่งเฉพาะไฟล์ `.md`: สคริปต์และไฟล์ประกอบของ skill ไม่ได้ถูกส่ง เอกสารถูกประกอบกลับจากชิ้นด้วย `GET /v1/memories?brain=&subject=` และดูรายการที่เก็บไว้ด้วย `GET /v1/subjects?brain=&prefix=`

## ตัดสินใจอย่างไร

1. ตัดคำของคำค้น ภาษาไทยใช้ `Intl.Segmenter` ส่วนรหัสเก็บไว้ทั้งก้อน
2. ถ้าคำค้นมีชื่อที่ลงทะเบียนไว้ จะเหลือเฉพาะความจำที่พูดถึงชื่อนั้น ถ้าคำนำหน้าอย่าง "ลูกค้า" ตามด้วยคำที่ไม่เคยปรากฏในความจำของสมองนี้เลย จะไม่ตอบ พร้อม `reason: "unknown_entity"`
3. ดึงผู้สมัครจากความคล้ายของเวกเตอร์และจากการค้นด้วยคำ
4. ตัดผู้สมัครที่ไม่มีรหัสตามที่คำค้นถาม
5. ให้คะแนนจากความคล้ายที่ปรับสเกลแล้ว รวมกับสัดส่วนคำของคำค้นที่พบในความจำ รายการที่ต่ำกว่า `minScore` ถูกทิ้ง ถ้าไม่เหลือเลยจะได้ `abstained: true`

เกณฑ์อยู่ใน `src/config.ts` และได้มาจาก `bun run eval` ซึ่งปรับบนคำถามครึ่งหนึ่งแล้วรายงานผลบนอีกครึ่ง

## ปัญญา 3

ความจำแต่ละรายการติดป้ายหมวดปัญญา 3 ได้ ป้ายนี้บอกว่าความรู้มาจากไหน ไม่ได้บอกว่าเป็นเรื่องอะไร:

| `panya` | ชื่อ | ความรู้มาจาก |
|---|---|---|
| `suta` | สุตมยปัญญา | การฟังและการเรียนรู้: อ่านมา มีคนบอก เอกสาร สเปก กฎระเบียบ |
| `cinta` | จินตมยปัญญา | การคิดพิจารณา: วิเคราะห์ ข้อสรุป การตัดสินใจพร้อมเหตุผล แผน |
| `bhavana` | ภาวนามยปัญญา | การลงมือปฏิบัติและฝึกฝน: บทเรียน ประสบการณ์ตรง สิ่งที่ลองแล้วได้ผลหรือไม่ได้ผล |

- ส่ง `panya` มากับความจำเพื่อระบุหมวดเอง ป้ายที่ผู้ใช้ระบุจะไม่ถูกติดทับ
- ถ้าไม่ระบุ **ผู้คุมสมอง** (governor) จะติดป้ายให้ ผู้คุมสมองติดป้ายอย่างเดียว ไม่เขียนหรือแก้ข้อความ
- ค้นเฉพาะหมวดด้วย `"panya": "bhavana"` หรือ `"panya": ["suta", "cinta"]` หน้าสมองมีตัวกรองเดียวกัน
- แก้ป้ายด้วย `PATCH /v1/memories/:id` ส่ง `{ brain, panya }` (ส่ง `""` เพื่อล้างป้าย)
- ทุกรายการมี `panyaBy` (`user`, `proto` หรือ `llm`) และ `panyaConf` (0-1) จึงแยกได้ว่าป้ายไหนระบบเดา ป้ายไหนคนเลือก

ผู้คุมสมองมีสองแบบ

- **proto** (ค่าเริ่มต้น) เทียบเวกเตอร์ของความจำ (ซึ่งคำนวณอยู่แล้วตอนบันทึก) กับประโยคตัวอย่างของแต่ละหมวด ร่วมกับคำบ่งชี้ เวลาบันทึกแทบไม่เพิ่ม และรันบนเครื่องคลาวด์ 4 GB ได้
- **ollama** ใช้โมเดลภาษาในเครื่อง (ค่าเริ่มต้น `qwen3:4b-instruct`) ให้ตอบเป็นคำเดียว แม่นกว่า แต่ใช้ 1-3 วินาทีต่อรายการบน CPU โน้ตบุ๊ก ใช้กับงานติดป้ายย้อนหลังเท่านั้น ไม่ใช้ตอนบันทึก: `bun run govern <brain> --mode ollama` ป้ายของผู้ใช้จะถูกข้าม และถ้า Ollama ล้ม ความจำนั้นยังคงป้ายจาก proto

ตั้งค่าด้วย `PANYA_GOVERNOR` (`proto`, `ollama` หรือ `off`), `PANYA_OLLAMA_URL`, `PANYA_GOVERNOR_MODEL`

วัดเมื่อ 9 พ.ย. 2026 (`bun eval/govern.ts --ollama`) ชุดแยกมี 30 ประโยค เขียนหลังจากกำหนดคำบ่งชี้เสร็จแล้ว และไม่เคยใช้ปรับค่า

| ผู้คุมสมอง | holdout (36) | ชุดแยก (30) | เวลาต่อรายการ |
|---|---|---|---|
| proto เวกเตอร์อย่างเดียว | 67% | ไม่ได้วัด | ราว 20 ms |
| proto เวกเตอร์ + คำบ่งชี้ | 97% | 77% | ราว 20 ms |
| ollama `qwen3:4b-instruct` | 92% | 90% | ราว 1.7 วินาที |

ตัวเลข holdout ของ proto ต้องอ่านอย่างระวัง เพราะคนเขียนคำบ่งชี้เคยเห็นประโยคชุดนั้นมาก่อน ตัวเลขที่ควรเชื่อคือชุดแยก (77%) ระหว่างทางมีปัญหาสองข้อ และโค้ดรับมือไว้แล้ว: `qwen3:4b` (รุ่นที่คิดก่อนตอบ) ไม่ฟัง `think: false` และใช้ราว 60 วินาทีต่อรายการ ส่วนการบังคับ JSON แบบ enum ทำให้โมเดลตอบ `suta` ทุกข้อ

โมเดลที่เล็กกว่านี้ลองแล้วเมื่อ 10 พฤศจิกายน 2026 ไม่มีตัวไหนใช้ได้ ทุกตัวได้ต่ำกว่าแบบ proto บนชุดแยก `qwen3:4b-instruct` จึงยังเป็นตัวเล็กที่สุดที่คุ้มจะรัน

| โมเดล (Ollama) | ขนาด | holdout (36) | ชุดแยก (30) | เวลาต่อรายการ |
|---|---|---|---|---|
| `qwen3:1.7b` | 1.4 GB | 78% | 50% | ราว 0.9 วินาที |
| `qwen2.5:1.5b` | 1.0 GB | 72% | 43% | ราว 0.7 วินาที |
| `qwen3:0.6b` | 0.5 GB | 56% | ไม่ได้วัด | ราว 0.5 วินาที |
| `llama3.2:1b` | 1.3 GB | 33% | ไม่ได้วัด | ราว 1.0 วินาที |
| `gemma3:1b` | 0.8 GB | 33% | ไม่ได้วัด | ราว 2.2 วินาที |

## เอกสารยาวและการตัดท่อน

`POST /v1/documents` ส่ง `{ brain, text, source, panya?, max?, overlap?, headings? }` ตัดเอกสาร Markdown หรือข้อความธรรมดาเป็นท่อน แล้วเก็บแต่ละท่อนเป็นความจำที่มี `ref = source#ลำดับ`

- ไม่ตัดข้ามหัวข้อ และแต่ละท่อนประกอบจากบรรทัดหรือประโยคเต็ม
- `headings` (เปิดเป็นค่าเริ่มต้น) แนบเส้นทางหัวข้อ เช่น `คู่มือสาขา › บางนา › เวลาทำการ` ไว้หน้าทุกท่อน ข้อความที่ซ้ำกันในหลายหัวข้อจึงยังรู้ว่าเป็นของหัวข้อไหน
- `overlap` ยกประโยคท้ายของท่อนก่อนมาไว้ต้นท่อนถัดไป
- ส่ง `source` เดิมซ้ำ = แทนที่ท่อนชุดเก่าของเอกสารนั้นทั้งหมด
- ถ้ามีท่อนใดมีความลับ จะไม่บันทึกอะไรเลย

ค่าเริ่มต้น (`max 300, overlap 120, headings เปิด`) เลือกด้วย `bun eval/chunks.ts` จากเอกสารแต่งขึ้น 4 ฉบับ และคำถาม 57 ข้อ (มีคำตอบในเอกสาร 50 ข้อ ไม่มี 7 ข้อ) ท่อนจะนับว่าเกี่ยวข้องเมื่อมีข้อความคำตอบครบทั้งท่อน

| วิธีตัด | R@1 | R@3 | MRR | nDCG@5 | ไม่ตอบเมื่อไม่มีคำตอบ |
|---|---|---|---|---|---|
| ย่อหน้า 700 (ตัวนำเข้าสกิลและไฟล์ความจำ) | 86% | 96% | 0.914 | 0.919 | 29% |
| ประโยค 300 ไม่แนบหัวข้อ | 80% | 98% | 0.892 | 0.904 | 71% |
| **ประโยค 300 ซ้อน 120 แนบหัวข้อ** | **92%** | **100%** | **0.957** | **0.944** | **71%** |

ตัวนำเข้าความจำและสกิลของ Claude Code ยังใช้ตัวตัดตามย่อหน้าโดยตั้งใจ เพราะต้องประกอบกลับเป็นไฟล์เดิมให้ตรงทุกไบต์ การแนบหัวข้อหรือการซ้อนท่อนจะทำให้ประกอบกลับไม่ได้ ชุดทดสอบนี้เล็ก และค่าเริ่มต้นถูกเลือกบนชุดเดียวกันนี้ จึงควรวัดซ้ำกับเอกสารของคุณเอง

`bun eval/run.ts` รายงาน MRR และ nDCG@5 เพิ่มจากอันดับ 1 และ 3 อันดับแรกแล้ว

## ไฟล์: เอกสาร เสียง วิดีโอ ภาพ

`POST /v1/files` รับไฟล์ได้ทุกชนิด ดึงข้อความออกมาแล้วเก็บแบบเดียวกับ `/v1/documents` ค่า source ตั้งต้นคือชื่อไฟล์ อัปไฟล์ชื่อเดิมซ้ำจึงแทนที่ท่อนชุดเก่า panya เก็บเฉพาะข้อความ ไม่เก็บตัวไฟล์ ในหน้าสมองใช้ปุ่ม **เพิ่มไฟล์** หรือลากไฟล์มาวางบนภาพสมอง

| ชนิด | ไฟล์ | อ่านข้อความอย่างไร |
|---|---|---|
| เอกสาร | PDF, Word (`docx`), PowerPoint (`pptx` รวมโน้ตผู้บรรยาย), Excel (`xlsx`), OpenDocument (`odt` `odp` `ods`), EPUB, RTF, HTML | อ่านด้วย JavaScript ไม่ต้องลงโปรแกรมเพิ่ม หน้า สไลด์ และชีตกลายเป็นหัวข้อ ทุกท่อนจึงบอกได้ว่ามาจากตรงไหน แถวตารางเป็น `คอลัมน์: ค่า · คอลัมน์: ค่า` |
| ข้อความ | `txt` `md` `csv` `tsv` `json` `srt` `vtt` และไฟล์ข้อความอื่น ๆ (โค้ด log ไฟล์ตั้งค่า) | UTF-8, UTF-16 หรือ TIS-620 (ไฟล์ไทยรุ่นเก่า) |
| เสียงและวิดีโอ | `mp3` `wav` `m4a` `ogg` `flac` `mp4` `mov` `mkv` `webm` และอื่น ๆ | ถอดเสียงพูดด้วย [faster-whisper](https://github.com/SYSTRAN/faster-whisper) (`large-v3-turbo`) ผ่าน `scripts/transcribe.py` ทุกบรรทัดมีเวลากำกับ เช่น `[1:05] ...` |
| ภาพ | `png` `jpg` `webp` `tiff` `bmp` `gif` | OCR ด้วย Tesseract (`tha+eng`) |

ข้อความที่ได้คือคำในไฟล์เอง การถอดเสียงและ OCR แค่ถอดตามที่มี ไม่สรุปหรือเขียนใหม่ ทุกท่อนผ่านการตรวจความลับแบบเดียวกับความจำทั่วไป

เสียง วิดีโอ และภาพ ต้องมีโปรแกรมบนเซิร์ฟเวอร์ ซึ่งจะเปิดใช้เองเมื่อหาโปรแกรมเจอ (ดูได้ที่ `GET /v1/files/types`)

- เสียง: `pip install faster-whisper` โมเดล (ราว 800 MB) จะดาวน์โหลดตอนใช้ครั้งแรก วิดีโอใช้ได้โดยไม่ต้องมี ffmpeg
- OCR: Tesseract พร้อมชุดภาษาไทย อิมเมจ Docker มีให้แล้ว
- อิมเมจ Docker ไม่มีตัวถอดเสียง เพราะต้องใช้ Python และช้าเกินไปบนเครื่อง 4 GB ไฟล์เสียงและวิดีโอให้ส่งเข้า panya ที่รันบนเครื่องที่ลง faster-whisper ไว้

ค่าตั้ง: `PANYA_UPLOAD_MAX_MB` (ค่าเริ่มต้น 200 ถ้าใช้ Cloudflare แบบฟรีจะอัปได้ไม่เกิน 100 MB), `PANYA_ASR` และ `PANYA_OCR` (`off` = ปิด), `PANYA_PYTHON`, `PANYA_ASR_MODEL`, `PANYA_ASR_LANG` (ว่าง = ตรวจภาษาเอง), `PANYA_TESSERACT`, `PANYA_OCR_LANG`

สิ่งที่ตรวจแล้วเมื่อ 10 พฤศจิกายน 2026 (`bun test test/files.test.ts`):

- เสียง: เสียงพูดไทย 45 วินาที `large-v3-turbo` ถูกเกือบทุกคำ ใช้เวลา 39 วินาทีบน CPU ของโน้ตบุ๊กเครื่องนี้ ส่วน `small` ใช้ 393 วินาทีและผิดมากกว่ามาก Whisper ที่รันใน Bun (transformers.js) พูดคำเดิมซ้ำอย่างเดียว จึงไม่ใช้
- OCR: ราว 0.6 วินาทีต่อภาพในอิมเมจ Docker ตัวเลขและภาษาอังกฤษถูก ภาษาไทยบางทีหล่นวรรณยุกต์ (หนี้ เป็น หนี)
- PDF: PDF ภาษาไทยบางไฟล์เก็บตัวอักษรแบบที่ pdf.js อ่านกลับไม่ได้ ในไฟล์ทดสอบ น้ำ ออกมาเป็น นำ
- คำถอดจากเสียงตัดท่อนละ 150 ตัวอักษร ไม่ใช่ 300 ในคลิปทดสอบ คำถามที่ไม่ได้ใช้คำเดียวกับในคลิปได้คะแนน 0.38 แทน 0.27 วัดจากคลิปเดียว ยังไม่ใช่ผลวัดจริงจัง
- ยังไม่รองรับ: ไฟล์ Office รุ่นเก่าแบบไบนารี (`doc` `xls` `ppt` ให้บันทึกเป็น `docx` `xlsx` `pptx`) และ PDF ที่สแกนมาโดยไม่มีชั้นข้อความ (ให้ส่งออกเป็นภาพก่อน)

ไฟล์ที่อัปจะถูกอ่านทีละไฟล์อยู่เบื้องหลัง รายการงานเก็บในหน่วยความจำ จึงหายเมื่อเริ่มเซิร์ฟเวอร์ใหม่

## Reranker (ตัวเลือกเสริม)

cross-encoder ขนาดเล็ก (`onnx-community/bge-reranker-v2-m3-ONNX` รันผ่าน transformers.js เหมือนตัว embedding) ให้คะแนนคู่ (คำถาม, ความจำ) ทีละคู่ในกลุ่มผู้สมัครอันดับต้น แล้วผสมกับคะแนนเดิม มันให้คะแนนอย่างเดียว ไม่เขียนและไม่แก้ข้อความใดเลย

ค่าตั้งต้นคือปิด

- `PANYA_RERANK=1` เปิดใช้งาน
- `PANYA_RERANK_TOP` (ค่าตั้งต้น 10) คือจำนวนผู้สมัครอันดับต้นที่ถูกให้คะแนนใหม่
- `PANYA_RERANK_WEIGHT` (ค่าตั้งต้น 0.7) และ `PANYA_RERANK_MIN_SCORE` (ค่าตั้งต้น 0.2) คุมสัดส่วนการผสมและเกณฑ์ตัดทิ้ง
- คำขอแต่ละครั้งข้ามได้ด้วย `"rerank": false` ใน `POST /v1/search` และผลลัพธ์จะมี `"reranked": true` เมื่อ reranker ทำงาน
- สำหรับ Docker ใช้ `--build-arg BAKE_RERANKER=1` เพื่อฝังโมเดล (ราว 570 MB) ลงใน image

วัดเมื่อ 12 ตุลาคม 2026 บน CPU ของโน้ตบุ๊ก (Intel i7-1165G7 ไม่มีการ์ดจอแยก) ชุดวัดผลคือความจำไทยสมมติ 100 ข้อ รวมกับความจำจริง 7,088 ข้อเป็นตัวลวง และคำถาม 120 ข้อ

| การตั้งค่า | ถูกที่อันดับ 1 | ไม่ตอบเมื่อไม่มีคำตอบ | เวลาค้นเฉลี่ย |
|---|---|---|---|
| เกณฑ์ตั้งต้น | 82% | 60% | 81 ms |
| ปรับเกณฑ์ใหม่ ไม่ใช้ reranker (`lexWeight=0.5 simFloor=0.84 simCeil=0.9 minScore=0.4`) | 79% | 90% | 81 ms |
| Reranker อันดับต้น 5 รายการ | 82% | 95% | 1,700 ms (p95 4,300 ms) |

แถวแรกคือคำถามทั้ง 120 ข้อด้วยค่าตั้งต้นที่มากับโปรแกรม อีกสองแถวคือคำถาม 60 ข้อที่กันไว้ หลังปรับเกณฑ์บนอีก 60 ข้อ

อ่านผลนี้ตามจริง บน CPU ผลที่ดีขึ้นส่วนใหญ่ได้มาฟรีจากการปรับเกณฑ์ใหม่ด้วยข้อมูลของคุณเอง reranker เพิ่มได้อีกไม่กี่จุดโดยแลกกับเวลาค้นที่นานขึ้นมาก จึงคุ้มเป็นหลักเมื่อมี GPU หรือเมื่อมีคำค้นไม่บ่อย

เคยลอง reranker ที่เล็กกว่าอีกสองตัวแล้วไม่ใช้: `Xenova/bge-reranker-base` ทำให้ความถูกต้องที่อันดับ 1 ของภาษาไทยลดเหลือ 72% และ `gte-multilingual-reranker-base` โหลดใน transformers.js ไม่ได้

รันซ้ำได้ด้วย `bun eval/run.ts --rerank --haystack <brain>[:<count>]`

## ผลวัด

ความจำไทยสมมติ 100 ข้อ และคำถาม 120 ข้อ (ใช้คำตรงกัน 36 ถามด้วยคำอื่น 42 นอกเรื่อง 16 อยู่ในโดเมนแต่ไม่มีคำตอบ 26) ตัวเลขด้านล่างมาจากคำถาม 60 ข้อที่ไม่ได้ใช้ปรับเกณฑ์ วัดเมื่อ 7 ตุลาคม 2026 บนโน้ตบุ๊ก Windows

| ชุดที่ไม่ได้ใช้ปรับเกณฑ์ | panya | supermemory ค่าตั้งต้น | supermemory ตั้งเกณฑ์คะแนน |
|---|---|---|---|
| ถูกที่อันดับ 1 | 82% | 85% | 44% |
| ถูกใน 3 อันดับแรก | 90% | 92% | 44% |
| ไม่ตอบทั้งที่มีคำตอบ | 10% | 3% | 56% |
| ไม่ตอบเมื่อไม่มีคำตอบ | 76% | 0% | 100% |
| เวลาค้นเฉลี่ย | 20 ms | 78 ms | 78 ms |

อ่านผลนี้ตามจริง panya **ไม่ได้**จัดอันดับเก่งกว่าตัวเทียบ การจัดอันดับพอ ๆ กัน สิ่งที่เพิ่มเข้ามาคือความสามารถในการไม่ตอบ ซึ่งเกณฑ์คะแนนค่าเดียวทำไม่ได้โดยไม่ทิ้งคำตอบจริงไปเกินครึ่ง

ตัวเทียบคือ supermemory แบบ self-host รุ่น 0.0.8 โหมดค้นเอกสาร ใช้ `multilingual-e5-base` และไม่ได้ตั้ง LLM โหมดสกัดความจำด้วย LLM ของมันยังไม่ได้วัด เพราะบน Gemini key แบบฟรีประมวลผลได้ราวนาทีละหนึ่งความจำ จึงหยุดไว้ก่อน

รันซ้ำได้ด้วย `bun run eval` และ `bun eval/baseline-supermemory.ts ingest|measure`

ความเร็ว จาก `bun run bench` เมื่อ 8 ตุลาคม 2026 (เครื่องเดิม seekdb รันใน Docker)

| การทำงาน | เวลา |
|---|---|
| ค้น คำค้นใหม่ | เฉลี่ย 18 ms, p95 30 ms |
| ค้น คำค้นซ้ำ (จำ embedding ไว้แล้ว) | เฉลี่ย 9 ms, p95 14 ms |
| ยิงค้น 120 คำค้นพร้อมกัน | 236 คำค้นต่อวินาที |
| บันทึกทีละรายการ | 25 ms ต่อรายการ |
| บันทึกผ่านเส้นทาง batch | 12 ms ต่อรายการ |

หน่วยความจำ: โปรเซส panya ใช้ราว 1 GB และ seekdb ระบุขั้นต่ำ 2 GB

## ข้อจำกัดที่รู้แล้ว

- คำถามที่ใช้คำห่างจากต้นฉบับมากยังพลาด (คำถามแบบถามด้วยคำอื่นถูกที่อันดับ 1 เพียง 67%)
- คำถามในโดเมนที่ไม่มีคำตอบยังถูกตอบราวหนึ่งในสี่ เช่น ถามจำนวนรถของผู้ขนส่งรายหนึ่ง จะได้ข้อเท็จจริงอื่นของรายนั้นกลับมา
- เมื่อสมองใบเดียวมีความจำหลายพันข้อ เกณฑ์ที่มากับโปรแกรมจะตอบง่ายเกินไป (การไม่ตอบอย่างถูกต้องลดเหลือ 60% เมื่อมีตัวลวง 7,088 ข้อ) ให้ปรับเกณฑ์ใหม่ด้วยการวัดแบบ haystack
- ตัวเลขโดดและตัวอักษรเดี่ยว ("ประตู 5", "โซน Z") ยังไม่ถูกมองเป็นรหัส
- ย่อข้อความเองไม่ได้ ให้ส่งมาทีละข้อเท็จจริงสั้น ๆ ไม่เกิน 2000 ตัวอักษร
- seekdb โหมด embedded ค้างบน Windows ทั้งใต้ Bun และ Node (ทดสอบ 7 ตุลาคม 2026) ให้ใช้แบบเซิร์ฟเวอร์ใน Docker
- image `oceanbase/seekdb` ไม่ใช้ค่า `ROOT_PASSWORD` ในการทดสอบของเรา รหัส root ว่างเปล่า ต้องตั้งด้วย SQL ก่อนเปิดพอร์ตให้เครื่องอื่น
- ชุดวัดผลยังเล็กและมาจากโดเมนเดียว ควรรันกับข้อมูลของคุณเองก่อนเชื่อเกณฑ์
